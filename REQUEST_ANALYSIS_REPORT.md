# PARTSINTEL Request & Parts Analyst

## Scope

Added standard-library modules `request_analyst.py`, `catalogue_parser.py`, and their shared decimal/alias helpers in `partsintel_common.py` under `agentic-2026-11-04.v2-initial/`. The analyst parses approved document evidence from the Document Intelligence Agent, analyzes projected requests and parts, and reports technical candidates. It does not dispatch, escalate, inspect, verify, or issue clarification actions. It does not modify `solution.py`, the official evaluator, simulator, or public datasets.

## Behavior

- Request parsing returns ticket ID, voltage, connector, minimum wattage, extracted constraint evidence, missing fields, ambiguity, confidence, and source document/text provenance.
- Catalogue parsing returns part ID, voltage, connector, wattage, connector aliases, evidence document, and stock snapshot metadata. Availability remains `null` until a matching successful inspect/verify result is supplied. Exact simulator tool result wrappers can be passed per part using `stock_results`.
- `mV`/`mW` are normalized to `V`/`W` with decimal strings to avoid float comparisons. Official connector aliases normalize to `USB-C`; barrel remains barrel. Missing values stay unknown.
- Obsolete, previous, retired, and explicitly disclaimed clauses are masked before extraction. Character offsets remain aligned to the original text. A numeric value explicitly labeled as voltage (v6 wording includes “input voltage is 12”) is preserved as volts and marked `unit_inferred_from_dimension_label` in provenance.
- Conflicting active values remain unknown. Unrecognized explicit constraints make compatibility unresolved rather than silently passing.
- Compatibility requires exact voltage and connector equality and part wattage >= request minimum. For an unknown request wattage, a matching known >=20 W part is technically compatible because v6 limits the request minimum to 10 W or 20 W. Otherwise the request remains unresolved and clarification is recommended only when no such candidate exists.
- Clarification is consumed only from the official `{ok: true, data: {ticket_id, reply}}` result, and only when the ticket ID matches and the reply contains one unambiguous wattage. No customer reply is generated by this module.
- Snapshot reliability follows the observed policy: recent snapshots are marked synchronized at batch open under ordinary policy; aged snapshots may be stale; when policy says only verify is authoritative, both age classes are untrusted. Snapshot reliability is kept separate from technical compatibility.

## Public data check

The unit suite analyzes every observation in `training.json` and `practice.json` using observation documents only, not evaluator `world` labels. All 312 request rows retained a parseable voltage and connector, and each minimum wattage was either unknown or normalized to 10 W/20 W. Each observation yielded six requests and twelve catalogue entries.

## Limits and integration

The parser is intentionally conservative and rule-based. It supports the released v6 prose patterns and explicit constraints; unsupported constraint language is returned as unresolved and may require an LLM interpretation in the later orchestration path. Candidate results describe technical compatibility only, not stock availability after previous dispatches and not an action choice. The Decision Planner must combine these results with stock verification policy, tool budget, shared inventory, and irreversible decision rules.
